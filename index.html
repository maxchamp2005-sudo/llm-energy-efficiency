Technical notes and measurement plan +
THE DECISION01 — 04

For operators with a choice to make

When two configurations both work, which one earns its place?

A model, serving stack, batching policy, or quantization change can alter energy use and service quality at the same time. A useful comparison holds the workload and acceptance rules steady, then measures what each configuration consumes.

This is for an enterprise team evaluating a specific deployment decision—not a universal data-center score. The pilot starts with one representative workload and a clear operational threshold for quality, time to first token (TTFT), and time per output token (TPOT).

Two boundaries, one workload

Read the wall.
Explain the device.

THE PILOT SHAPE03 — 04

Designed for an isolated environment

One bounded question.
One defensible comparison.

A candidate pilot correlates real supply energy with request and task logs, then uses GPU telemetry as a separate diagnostic. The deployment can be designed with a local collector and local results, with no outbound service calls; the meter’s own data path must be validated before the study.

A

Define the boundary

Choose the metered feeds and included equipment. Record exclusions such as cooling, UPS losses, or shared infrastructure.

B

Freeze the workload

Fix the task set, warm-up, sampling, and evaluation. Agree on quality acceptance, TTFT, and TPOT targets before comparing.

C

Align each run

Match meter readings, GPU counters, and request/task events to the same start and end. Repeat trials and retain failures.

D

Decide inside the gate

Compare Wh per accepted task only after each candidate clears the agreed service thresholds. Report uncertainty and boundary limits.

ADDED VALUE TO TEST

Tools such as NVIDIA DCGM, AIPerf, MLPerf, and Zeus address useful parts of GPU telemetry, benchmarking, or energy analysis. The pilot’s proposed added value is the aligned view across real supply energy, production-shaped task outcomes, quality, and latency under one fixed acceptance rule. Keep existing tools where they fit; test whether this combined evidence changes the decision.

THE BUSINESS CASE04 — 04

Translate carefully

Expose energy cost.
Earn the savings claim.

Metered consumption can make energy exposure legible. A lower lab result becomes a cash-savings estimate only after runtime, the tariff, and the applicable contract charges are verified.

01 / COST EXPOSUREMeasured energy × applicable rate × eligible runtime

Report the measured boundary and the rate used. Demand, capacity, fixed, and pass-through charges may not move with kWh.

02 / CONDITIONAL SAVINGSValidated energy delta × variable charges that actually change

Apply only to workloads that can adopt the eligible configuration. Confirm billing treatment and operational runtime before calling it cash savings.

Why the decision matters

Efficiency evidence helps operators use scarce capacity well.

Electricity supply and interconnection can move on a different schedule from data-center construction. The IEA describes grid expansion timelines of roughly 5–15 years in some cases, compared with 1–3 years for data centers. Measurement can inform workload and infrastructure choices; it cannot create feeder capacity, solve cooling constraints, or accelerate a utility connection.

Likewise, PUE describes facility overhead relative to IT energy. It does not say how efficiently a given model completes accepted work. An LLM workload metric fills a different question, with its own clearly declared boundary.

Instrumentation reality check

Current is useful.
Current is not energy.

Clamp and bench meters can help diagnose load, but neither named instrument is a direct W/Wh meter. Select an appropriately rated real-energy meter for the supply measurement.

Open instrument notes+
Fluke 376 FC

True-RMS clamp meter for AC/DC current diagnostics. Its current reading supports a load check; by itself it does not provide supply real power or cumulative Wh for this study. Confirm rated safe access and a fully local data path for any future workflow.

Illustrative values · browser calculation

Wh per accepted task = gross supply Wh ÷ quality-accepted tasks. Output tokens per kWh is a batch diagnostic; it is not quality-adjusted by itself. Average watts = gross Wh ÷ batch hours. These figures describe the whole measured batch and do not allocate causal energy to individual concurrent requests.
